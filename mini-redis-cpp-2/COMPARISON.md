# mini-redis-cpp 改进版对比

本文对比 `mini-redis-cpp-2/` 下三个改进版：

| 目录 | 基线（本仓库） | 定位 |
|---|---|---|
| `v1-baseline-hardened/` | `01-original`（原始项目 + 低级错误修正） | 保持最小规模，把会造成**数据损坏 / 崩溃 / 无法优雅退出**的结构性问题修掉 |
| `v2-fixed-robust/` | `02-fixed`（语义已对齐 Redis，仅 POSIX） | 在语义正确的基线上，把**数据完整性与资源安全**做成可测试的属性 |
| `v3-improved-scalable/` | `03-improved`（跨平台 + 协议健壮 + 完整测试） | 解决**规模化**问题：线程数与连接数解耦、落盘不长时间阻塞、过期清理不随 TTL 键数增长 |

> 三个改进版都是**重写级**的改动，不是对原文件的补丁。v1 建立正确的骨架，
> v2 在其上加固"信任边界"，v3 再在其上做并发与资源层面的解耦。
> 因此三版之间存在明确的递进关系：**v3 的能力集合 ⊃ v2 ⊃ v1**。

## 二、各版本解决的问题对照

### 2.1 数据正确性

| 问题（原始三版共同或各自存在） | v1 | v2 | v3 |
|---|---|---|---|
| 一个 key 可同时是 string + list + hash（`RENAME`/`LPUSH` 即可造出） | 修（单一键空间 + `variant`） | 继承 | 继承 |
| 值含空格/换行持久化后损坏 | 修（长度前缀二进制安全） | 继承 | 继承 |
| TTL 不落盘，重启后 key 变永久 | 修（记录剩余 TTL 毫秒） | 继承 | 继承 |
| 已过期的 key 被写进存档、重启后"复活" | 修（落盘前清理） | 继承 | 继承 |
| 落盘中途崩溃 → 旧档新档双失 | 修（`.tmp` + `rename`） | 增强（回读逐字节校验） | 继承 |
| `load()` 无法区分"文件不存在"与"文件损坏" | 修（`LoadResult` 四态） | 增强（+`LegacyFormat`，文件级 CRC） | 继承 |
| 存档被翻转一个字节后静默装载垃圾 | ❌ 只能发现格式错 | ✅ CRC32 检出 | ✅ |
| 过期 key 长期可见（清理依赖"恰好有人访问"） | 修（所有读路径都惰性删除） | 继承 | 增强（时间轮 + 内联 deadline 检查） |

### 2.2 崩溃与停机

| 问题 | v1 | v2 | v3 |
|---|---|---|---|
| 信号处理器里做 dump/加锁/`exit()`（异步信号不安全） | 修（只置标志 + 自管道） | 继承 | 继承 |
| 阻塞 `accept` 无法被信号唤醒 → 只能在 handler 里 `exit()` | 修（`waitReadable` 带超时轮询） | 继承 | 继承（+50ms 响应） |
| 退出时 `join` 因仍有客户端连接而永久卡住 | 修（先 close 所有连接再 join） | 继承 | 修（线程池先清队列、限时 join） |
| `SIGPIPE` 默认动作杀死进程 | 修（`SIG_IGN`） | 继承 | 继承 |
| 一次 `recv` 一条命令：>1KB 截断、粘包丢命令、半包腰斩 | 修（增量解析器） | 继承 | 继承（+零搬移） |
| 畸形协议回复不是 RESP（`Err: Empty command`） | 修（`-ERR Protocol error: ...`） | 继承 | 继承 |
| `std::stoi` 前缀截断（`12abc` → 12） | 修（自写严格十进制解析） | 继承 | 继承 |
| 端口不校验范围 → `htons` 静默截断 | 修 | 继承 | 继承 |
| `bind` 失败仍返回 0 | 修（退出码 1） | 继承 | 继承 |
| `detach` 的线程不被等待，进程可能在写数据时退出 | （v1 不 detach，逐连接 join） | 同 v1 | 修（线程池统一管理生命周期） |

### 2.3 资源与规模

| 问题 | v1 | v2 | v3 |
|---|---|---|---|
| 线程数随连接数线性增长 | ❌ 保留 | ❌ 保留 | ✅ 线程池（实测 +0 线程） |
| 无最大连接数 → 到上限时表现为 accept 失败退出 | ❌ 保留 | ❌ 保留 | ✅ 明确拒绝 + 计数 |
| 空闲连接永久占资源（慢速攻击面） | ❌ 保留 | ✅ 空闲超时 | ✅ 可热改超时 |
| 单个大写入可打爆内存 | ❌ 保留 | ✅ 内存上限 + `-OOM` | ✅ 可热改上限 |
| 落盘期间所有客户端被阻塞 | ❌ 保留 | ❌ 保留 | ✅ 锁内快照 + 锁外写盘 |
| 落盘重叠（后台 + 退出路径） | ❌ 保留 | ❌ 保留 | ✅ `Busy` 短路 |
| 每条命令都全表扫描过期表 | ❌ 保留 | ❌ 保留 | ✅ 时间轮 |
| 每次 `KEYS` 重编译正则 | （v1 起就用手写 glob） | 同 v1 | 同 v1 |
| 接收缓冲 `erase(0,n)` 的 O(n²) 搬移 | ❌ 保留（小缓冲下无感） | ❌ 保留 | ✅ 读游标 + 惰性压缩 |

## 三、实测数据

测试环境：Windows + MinGW-w64 g++ 16.1.0（`x86_64-win32-seh-rev1`）、CMake 4.3.3、
`-DCMAKE_BUILD_TYPE=Release`、`-Wall -Wextra -Wpedantic`。

### 3.1 编译与测试

```
版本                        编译警告  自检         集成测试
v1-baseline-hardened           0     104 / 0 失败   60 / 0 失败
v2-fixed-robust                0     124 / 0 失败   72 / 0 失败
v3-improved-scalable           0     151 / 0 失败   60 / 0 失败
```

### 3.2 线程数 vs 空闲连接数（50 个空闲 TCP 连接）

| 版本 | 启动后线程数 | 50 个空闲连接后 | 增量 |
|---|---|---|---|
| v1（每连接一线程） | 3 | **53** | +50 |
| v2（每连接一线程） | 3 | **53** | +50 |
| v3（`--threads 4`） | 8 | **8** | **+0** |

> 解读：v1/v2 的线程数 = 连接数 + 常数；v3 恒定。以每线程 1MB 栈估算，
> 10k 空闲连接在 v1/v2 上仅栈就约 10GB，v3 不变。

### 迁移兼容性

- `v1 → v2`：v2 能读 v1 的存档（报 `LegacyFormat`），退出时自动改写成新格式；反向不可读。
- `v2 ↔ v3`：**存档格式完全一致**（`MINIRDB2` + CRC32），可互相读取。
- 三版的命令行参数**向后兼容**：`v3-server` 接受 `v1/v2` 的全部参数（`--port/--dump`），
  另有新增的 `--threads/--maxclients/--dump-interval`。
- 三版的协议行为一致（同为 RESP2 文本协议，`-ERR`/`+OK`/`:n`/`$n`/`*n`），
  同一客户端可连接任意一版。

## 四、三版共同的"仍未解决"清单



1. **单机单进程**：无主从复制、无集群、无哨兵。
2. **全局单锁**：所有命令串行经过一把互斥锁（v3 也没有分片）。
3. **`KEYS` 是 O(全部键)**：三版都遍历全表；生产应使用游标式 `SCAN`（未实现）。
4. **无 AOF/增量持久化**：只有全量快照；v3 的快照在内存里会有约 2 倍数据量峰值。
5. **未实现 `RESP3`、`MULTI/EXEC`、发布订阅、`SCAN`/`EXPIRE` 的 `NX/XX/GT/LT`**。
6. **仅 IPv4**：`AF_INET` 固定，未做 IPv6 双栈。
7. **Windows 上没有 `fsync`**：只有 POSIX 分支调用；Windows 侧依赖 `flush` + 回读校验。
